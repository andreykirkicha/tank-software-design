# Архитектура: ports & adapters

Роли всех production-классов и интерфейсов отмечены в их Javadoc. Пакеты исходного
проекта сохранены; пакет сам по себе не определяет слой. Например, `level`
содержит порт, два адаптера и application-сервис.

Зависимости направлены внутрь: infrastructure → application → domain.
Домен не импортирует LibGDX, application, графику, ввод или файловые адаптеры.
Application работает с доменными объектами и контрактами портов. Конкретные
реализации выбирает `GameDesktopLauncher` — composition root приложения.

## Domain (entities и правила)

| Классы и интерфейсы | Ответственность |
| --- | --- |
| `Tank` | Сущность танка, здоровье, стрельба, контекст State |
| `Bullet`, `Tree` | Сущности пули и дерева |
| `GameField` | Агрегат объектов, занятость клеток, движение и столкновения |
| `Direction` | Значение направления и смещения |
| `GameObject`, `Movable`, `Obstacle` | Доменные контракты объектов; не внешние порты |
| `TankState`, `LightTankState`, `MediumTankState`, `HeavyTankState` | State: поведение танка в текущем состоянии |
| `TankStatePolicy`, `HealthTankStatePolicy` | Доменное правило выбора состояния |
| `GameFieldListener` | Выходной порт событий добавления и удаления объектов |

`GameFieldListener` принадлежит домену, потому что события публикует сам агрегат.
Слушатель получает доменные объекты; ему не нужны `Texture`, `Batch` или коды клавиш.

## Application (use cases)

| Классы и интерфейсы | Ответственность |
| --- | --- |
| `GameSession` | Входной порт обновления игры |
| `GameLoop` | Use case кадра: сбор команд → выполнение → обновление домена |
| `TankController` | Запрос следующей команды для свободного живого танка |
| `Command` | Внутренний контракт шаблона Command |
| `MoveCommand`, `ShootCommand`, `ToggleHealthBarsCommand` | Use cases перемещения, выстрела и переключения полосок |
| `RandomTankGenerator` | Заполнение свободных клеток танками; Random внедряется конструктором |
| `GameInput` | Выходной порт получения действий игрока |
| `ControlStrategy` | Выходной порт выбора команды танка |
| `HealthBarVisibility` | Выходной порт переключения полосок здоровья |
| `GameFieldLoader` | Выходной порт получения начального игрового поля |

## Infrastructure (adapters)

| Адаптеры и служебные классы | Порт / назначение |
| --- | --- |
| `GameDesktopLauncher` | Входной адаптер LibGDX для `GameSession`, сборка зависимостей и ресурсов |
| `InputHandler` | `GameInput`: перевод клавиш LibGDX в действия игрока |
| `KeyboardControlStrategy` | `ControlStrategy`: перевод действий `GameInput` в команды |
| `RandomControlStrategy` | `ControlStrategy`: выбор команд через Random |
| `FileGameFieldLoader` | `GameFieldLoader`: чтение текстовой карты из Reader/Path |
| `RandomGameFieldGenerator` | `GameFieldLoader`: процедурное создание уровня |
| `GameFieldGraphics` | `GameFieldListener` и `HealthBarVisibility`: отображение событий и переключение полосок |
| `TankGraphics`, `BulletGraphics`, `TreeGraphics`, `HealthBarGraphics` | Представления доменных объектов через LibGDX |
| `HealthBarGraphicsDecorator` | Декоратор представления танка |
| `ObjectGraphics` | Внутренний контракт графических адаптеров, зависит от LibGDX |
| `GdxGameUtils`, `TileMovement` | Инфраструктурные операции рисования и интерполяции |

Не каждый интерфейс является портом, а класс, который рисует объект, не обязательно
реализует порт напрямую: графические представления обслуживают `GameFieldGraphics`.
В частности, `ObjectGraphics` нельзя считать портом ядра: его API содержит `Batch`
и `Disposable` из LibGDX.

## Недостающие границы и внесённые изменения

1. `ToggleHealthBarsCommand` зависела от конкретного `GameFieldGraphics`.
   Добавлен выходной порт `HealthBarVisibility`; графический адаптер реализует его.
2. `KeyboardControlStrategy` зависела от конкретного `InputHandler`.
   Добавлен `GameInput`; обработчик клавиатуры реализует этот порт.
3. Use case кадра находился в `GameDesktopLauncher`, смешиваясь с запуском окна,
   ресурсами и рисованием. Он перенесён в `GameLoop`, реализующий входной порт
   `GameSession`. Игровой цикл теперь можно выполнить без окна и OpenGL.
4. `GameFieldLoader`, `ControlStrategy` и `GameFieldListener` уже обеспечивали нужные
   границы. Их роли и реализации явно отмечены в Javadoc.

Отдельные порты репозитория для `Tank` и `GameField` сейчас не нужны: игра хранит
объекты в памяти и не сохраняет их во внешней системе. `GameField` является
агрегатом, а не адаптером базы данных. Если появятся сохранения, сеть или повтор
игры, соответствующий use case должен получить отдельный порт и адаптер хранения
либо транспорта. Дополнительный слой абстракций над каждым классом не требуется.

## Расширение состояний танка

`Tank` делегирует текущему `TankState` длительность шага, возможность выстрела
и время перезарядки. `HealthTankStatePolicy` выбирает состояние при создании
и после каждого попадания:

| Здоровье относительно начального | Состояние | Время шага | Стрельба |
| --- | --- | --- | --- |
| >70% | `LightTankState` | 0,4 с | Каждые 0,4 с |
| 15–70%, включая обе границы | `MediumTankState` | 0,8 с | Каждые 0,4 с |
| <15%, включая 0 | `HeavyTankState` | 1,2 с | Запрещена |

Танк с начальным здоровьем 0 сразу тяжёлый. Правило удаления при здоровье меньше
нуля сохранено. Доли сравниваются целочисленно с использованием `long`, без ошибок
округления на границах и переполнения `int`.

`GameField` хранит пройденную долю клетки. При изменении состояния в движении
положение не скачет: оставшаяся часть пути проходится с новой скоростью.
Обе клетки остаются заняты до завершения шага. Уже начатая перезарядка сохраняет
оставшееся время; новое значение применяется при следующем выстреле.

Для нового состояния достаточно реализовать `TankState` и внедрить правило
`TankStatePolicy` через дополнительный конструктор `Tank`. Например, бустер может
возвращать состояние с шагом 0,2 с и перезарядкой 0,2 с, а после окончания эффекта
снова делегировать выбор `HealthTankStatePolicy`. При включении/окончании эффекта
вызывается `tank.refreshState()`. Игровые команды, графика и контроллер при этом
не меняются. Пример такого расширения проверяется в `TankStateTest`; сами бустеры
на поле не добавлены, поскольку это пример будущего расширения из задания.

`Tank.isReady()` означает завершение перезарядки и наличие живого танка.
`Tank.canShoot()` дополнительно учитывает текущее состояние. Это позволяет тяжёлому
танку получать команды движения. `Tank.shoot()` повторно проверяет состояние при
выполнении: команда выстрела, собранная до попадания, тоже будет отклонена.

## Проверка

`./gradlew test` запускает существующие тесты и новые `TankStateTest` и
`GameLoopTest`: границы 15/70%, нестандартное начальное здоровье, скорости,
переходы во время движения, запрет выстрелов, расширение бустером, порядок команд
и работа application через подставные реализации портов без графики.
